# DB 연동 작업 정리 (2026-08-19)

> 계획 원문: `~/.claude/plans/wobbly-forging-gem.md`
> 배경: "실제 서비스로 돌릴만큼 부족한 부분이 많다"는 지적에 따라 진행한 프로덕션
> 준비 점검 중, 사용자가 고른 세 우선순위(운영 안정성/업로드 안전장치/DB 연동) 중
> "기존 `src/smart_e_bl` 재사용"으로 DB 연동을 진행했다. 인증/보안은 범위 밖.

## 결론: 어디까지 됐는가

**전 단계(1~7) 완료, 실제 동작 확인됨.** 게이트웨이 API가 DB에 선적/서류/필드값을
영구 저장하고, 프론트엔드(S2 업로드)가 이제 그 API로 실제 저장한다. 브라우저로
업로드 → S3 필드 확인 → 새로고침까지 확인 완료(아래 7절).

---

## 1. 배경 — 진짜 블로커였던 것

DB 연동을 막던 진짜 문제는 `field_value_evidence_required_ck` 제약(자동 추출값은
반드시 근거 좌표 bbox를 가져야 함)이었는데, aiService `/extract` 응답에 애초에
bbox가 없었다. 이건 이 작업 이전 세션에서 근본 수정 완료됨
(`ocr/types.py`·`field_parser.py`·`doc_parser.py`·`draft.py`).

## 2. 세 갈래 필드명 불일치 문제와 해결

아래 세 어휘가 서로 정확히 안 맞았다.

- aiService `BL_FIELD_NAMES` (15개, `ocr/types.py`)
- 프론트 표시 어휘 (26개, `frontend/src/constants/domain.ts`의 `FIELD_LABEL`) —
  `vessel_voyage`, `place_and_date_of_issue` 같은 합성 필드 포함
- DB 카탈로그 (28개 `BL.*` 코드, `migrations/sql/09_seed_catalog.sql`)

### 해결 규칙

| aiService 필드 | 처리 | DB 코드 |
|---|---|---|
| `vessel` + `voyage_no` | 프론트 어댑터에서 `"{vessel} / {voyage_no}"`로 합치고 bbox는 합집합 | `BL.VESSEL_VOYAGE` |
| `on_board_date` | `shipped_on_board_date`로 이름만 맞춤 | `BL.ONBOARD_DATE` |
| `place_of_issue` / `date_of_issue` | **사용자 결정: 합치지 않고 DB에 각각 별도 저장** (근거 좌표가 서로 다른 별개 필드라서) | `BL.PLACE_OF_ISSUE` / `BL.DATE_OF_ISSUE` |
| `total_freight` | 프론트 26개 필드에도 DB 카탈로그에도 대응 자리가 없어 저장하지 않고 버림 | 없음 (새 마이그레이션은 범위 밖) |
| 나머지 9개 | 이름이 이미 일치 (대문자 변환만) | `BL.{NAME}` |

`place_of_issue`/`date_of_issue`를 프론트에 노출하기 위해 `constants/domain.ts`의
`FIELD_LABEL`에 두 항목(`발행지`, `발행일`)을 추가했다. 기존 `place_and_date_of_issue`
(합성 표시용, `발행지·발행일`)는 그대로 유지 — 특별 처리하는 렌더링 코드가 없음을
확인함.

## 3. 발견한 기존 버그와 수정

`frontend/src/api/adaptersExtract.ts`의 `toFieldValue`가 bbox 수정 이전 시점 주석을
그대로 남긴 채 `field.name`을 무매핑으로 통과시키고 `bbox`·`page`를 항상 `null`로
고정하고 있었다 — bbox가 실제로 오는 지금 시점엔 사실이 아닌 stale 코드였다.
아래 파일들을 함께 고쳤다.

- `frontend/src/api/wireExtract.ts` — `WireDraftField`에 `bbox: [number,number,number,number] | null` 타입 추가.
- `frontend/src/api/adaptersExtract.ts` — 필드명 매핑(위 표), 실제 bbox 전달, vessel+voyage_no 합성 로직 추가.
- `frontend/src/api/extract.ts` — 호출자가 아는 페이지 번호(0-idx)를 1-idx로 바꿔 어댑터에 전달 (`field_value_page_ck`가 1 이상 요구).

`npx tsc --noEmit` 통과 확인. (이 프론트 프로젝트엔 테스트 러너가 아예 없어
자동화된 테스트는 남기지 못함 — 타입체크 + 수동 검증으로 대체.)

## 4. 게이트웨이 API — 새 엔드포인트 5개

`src/smart_e_bl/api/main.py`에 추가. 인증이 없어 모든 선적은 고정 부트스트랩
테넌트/사용자에 붙는다 (`migrations/sql/10_bootstrap_tenant.sql`,
`config.py`의 `BOOTSTRAP_TENANT_ID`/`BOOTSTRAP_USER_ID`).

| 메서드 | 경로 | 설명 |
|---|---|---|
| POST | `/api/v1/shipments` | DRAFT 선적 생성 |
| GET | `/api/v1/shipments` | 목록 (최신순) |
| GET | `/api/v1/shipments/{id}` | 선적 + 대표 필드값 |
| POST | `/api/v1/shipments/{id}/documents` | 서류 업로드 (multipart) |
| PUT | `/api/v1/shipments/{id}/fields` | 필드값 일괄 upsert |

### 설계 포인트

- **업로드 안전장치**: 30MB 초과 시 413(DB CHECK 제약과 동일 상한을 앞단에서 먼저
  차단), 확장자 화이트리스트(`.jpg/.jpeg/.png/.tif/.pdf`) 아니면 415, 서버가 직접
  sha256을 계산(클라이언트 신고 해시를 신뢰하지 않음). 같은 선적에 같은 해시 재업로드 시
  에러 대신 기존 `document_id`를 반환 (`document_shipment_hash_uk` 유니크 인덱스 활용,
  content-addressed 저장이라 디스크 중복도 안 생김).
- **extractor 종류 판단**: 프론트 타입엔 `'manual'`이 없는데 DB의
  `field_value_evidence_required_ck`는 `MANUAL`/`JSON`만 좌표 없이 저장을 허용한다.
  그래서 프론트가 보낸 라벨을 그대로 믿지 않고, **bbox 유무로 게이트웨이가 직접
  판단**한다 — bbox 있으면 `RULE`/`OCR_LLM`, 없으면 `JSON`이 아닌 한 `MANUAL`로 강제.
  제약을 항상 만족시키는 root-cause 설계.
- **NOT_FOUND 값 무효화**: `grade='NOT_FOUND'`인데 `value`가 오면 게이트웨이가
  `None`으로 강제해 `field_value_not_found_ck` 위반을 사전 차단.
- **저장 경로**: `src/smart_e_bl/storage.py` — sha256 앞 2자로 서브디렉터리를 나눠
  콘텐츠 주소로 저장 (`{root}/{hash[:2]}/{hash}{ext}`). 업로드 파일명은 저장 경로에
  전혀 안 씀 (경로 조작 방지), `original_filename`은 메타데이터 컬럼에만 남김.

## 5. Docker / 마이그레이션

- `infra/docker/gateway.Dockerfile` (신규) — uv 프로젝트라 `uv sync --frozen`
  사용(aiService의 pip 방식과 다름). 빌드 컨텍스트는 repo 루트(`pyproject.toml`이
  루트에 있어서).
- `docker-compose.yml`에 `api` 서비스 추가 — 포트 `8001:8000`, 새 볼륨
  `document-storage`를 `/data/documents`에 마운트, healthcheck는 기존 `/health`
  엔드포인트 재사용, `depends_on: postgres: condition: service_healthy`.
- `uv run alembic upgrade head`를 로컬에서 실행해 스키마 생성 (DB가 0개 테이블
  상태였음 — 이번에 처음 적용). 부트스트랩 테넌트/사용자 시드 포함.

### 실제 검증 결과

- `docker compose build api && docker compose up -d api` → `smart-ebl-api` 컨테이너
  `healthy` 확인.
- curl로 전체 흐름 확인: 선적 생성 → 이미지 업로드 → 필드 저장(bbox 있는 값,
  `place_of_issue`/`date_of_issue` 별도 행, `total_freight` 스킵) → 목록/상세 조회.
- 재업로드 시 같은 `document_id` 반환 확인, 잘못된 확장자 415, 30MB 초과 413,
  없는 선적 조회 404 확인.
- 검증에 쓴 테스트 데이터는 DB에서 정리 완료 (운영 데이터 아님).

## 6. 프론트엔드 재배선 (7단계, 완료)

`frontend/src/shared/shipmentStore.tsx`를 `sessionStorage`에서 실제 게이트웨이
API로 재배선했다.

- 새 파일 `frontend/src/api/{wireShipment,adaptersShipment,shipment}.ts` —
  F1~F4(`*Extract.ts`)와 같은 3단 분리 패턴(wire 타입 → 번역 → 실제 fetch).
  `client.ts`에 `GATEWAY_API_BASE_URL`·`getJson`·`putJson`을 추가하고
  `postJson`/`postForm`에 `baseUrl` 파라미터를 얹어 aiService 호출과 공존시켰다
  (`vite.config.ts`에 `/gw-api` 개발용 프록시도 같은 방식으로 추가).
- `createDraft`가 `(file, fields) => Promise<string>`으로 바뀌어
  `POST /shipments` → `POST /shipments/{id}/documents` →
  `PUT /shipments/{id}/fields` → (DB가 채운 `created_at` 등을 지어내지 않으려고)
  `GET /shipments/{id}` 순서로 호출한다. 유일한 호출부였던
  `S2Upload/index.tsx`도 `await`+에러 처리(`try/catch` → `FAILED` 상태 표시)로 맞춰 고쳤다.
- 목록 화면은 Provider가 마운트될 때 `GET /shipments` 후 선적마다
  `GET /shipments/{id}`를 한 번씩 더 불러 필드값까지 채운다(N+1, `ponytail:` 주석
  남김 — 지금은 선적 수가 적어 문제없고, 늘어나면 목록 응답에 필드를 같이 주도록
  게이트웨이를 고칠 것).
- `sessionStorage` 캐시(`readStored`/`writeStored` 등) 완전히 제거.
  mock 4건(`SHP-001~004`)은 그대로 프론트 픽스처로 남아 실제 DB와 무관하게 동작.
- 판정·하자확률·경보·현실 대조·영향분석(S4~S8)은 아직 백엔드가 계산하지 않으므로,
  실제 DB 선적도 그 부분은 기존 `buildDraftDataFromFields`가 빈 값으로 채운다
  (이번 작업으로 새로 생긴 제약이 아니라 원래 이번 기간 범위 밖).

### 실제 검증 결과 (브라우저)

- 로컬 `vite` 개발 서버(포트 5173, `/gw-api`→`8001`, `/ai-api`→`5050`)로 S2에서
  실제 PDF 업로드 → aiService 추출 → 게이트웨이 저장까지 성공, `/shipments/{UUID}/draft`로
  이동해 S3에 필드 13건이 렌더링됨을 확인.
  같은 URL을 완전히 새로고침해도 동일하게 뜨는 것으로 DB 영속(= 탭을 닫아도 유지)을 확인.
  S1 대시보드 목록에도 새 선적이 최신순으로 나타남을 확인.
- 이 과정에서 **버그 하나 발견 후 수정**: `smart-ebl-api` 컨테이너가 8시간 전
  이미지 그대로 떠 있어 4절의 `ShipmentDetailResponse` 필드 완성 수정(이전 세션)이
  반영되지 않은 상태였다. `bl_no`/`created_at`/`updated_at` 등이 응답에서 아예
  빠지면서 화면에 `D-NaN`, `NaN-NaN NaN:NaN`이 떴다. `docker compose build api &&
  docker compose up -d api`로 재빌드·재기동해 해결(코드는 이미 맞았고, 컨테이너가
  구버전이었을 뿐). 검증에 쓴 테스트 선적은 DB에서 정리 완료.
- `npx tsc --noEmit`, `npm run build`, `npm run lint`(oxlint, 기존과 동일한 경고만) 통과.

### 알아두면 좋은 것

- `docker-compose.yml`의 `frontend` 서비스(정적 빌드, 포트 8080)는 이번 프론트
  변경분을 아직 반영하지 않은 이전 빌드다. 실제로 그 화면에서 확인하려면
  `docker compose build frontend && docker compose up -d frontend` 필요(요청 시 진행).
- 코드를 고쳤는데 컨테이너가 안 바뀐 것처럼 보이면, 이번처럼 이미지가 오래됐을
  가능성부터 의심할 것 — `docker compose ps`의 `CREATED` 시각으로 바로 확인 가능.
