# F3 계층 B — 하자 확률 예측 모델 설계

기획안 5.3 계층 B, 10.1(구현 범위), 10.3(합성 데이터셋), 10.4(측정 설계)의 구현 설계서.
DB 스키마는 이미 확정되어 있다 — `migrations/sql/06_verdicts_and_predictions.sql`,
`src/smart_e_bl/models/verdicts.py` (`model_version`, `defect_prediction`, `prediction_factor`).
본 문서는 그 스키마를 채우는 코드의 설계를 규정한다.

---

## 0. 이 설계가 지키려는 것

기획안 10.4의 성공 판정은 다음과 같다.

> 결합 조건 F1 0.85 이상이며 **룰 단독 대비 개선이 확인될 것**

이 한 문장이 설계 전체를 규정한다. "룰 단독 대비 개선"을 측정 가능하게 만드는 것이
이 모델의 존재 이유이며, 아래 1절의 제약을 어기면 그 측정이 원천적으로 불가능해진다.

## 1. 최우선 제약 — 라벨 누수 차단

### 문제

기획안대로 순진하게 구현하면 다음이 성립한다.

- 피처군 1 = 룰별 위반 여부 벡터 (기획안 5.3)
- 합성 데이터는 "하자를 주입하면서 반응해야 할 rule_id를 정답 라벨로 기록" (10.3 ③)
- 모의 심사도 "룰 기반" (10.4)

→ `y = f(룰 발화)` 가 되어 모델이 룰엔진을 그대로 암기한다.
F1은 0.99가 나오지만 룰 단독 대비 개선폭은 정확히 0이고, 논문의 핵심 주장이 사라진다.

### 해법 — 두 개의 독립 노이즈 채널

주입된 하자(ground truth)로부터 **서로 독립인 두 경로**로 파생시킨다.

```
                     ┌─────────────────────────────┐
                     │  주입 하자 (ground truth)    │
                     │  injected_defects[]         │
                     └──────────┬──────────────────┘
                                │
              ┌─────────────────┴─────────────────┐
              │                                   │
     [채널 A] 룰 발화 시뮬레이터            [채널 B] 모의 심사기
     synth/rule_sim.py                     synth/review.py
              │                                   │
     · 룰이 커버하는 하자만 발화          · ICC 하자 유형별 은행 적발 확률
     · False Negative 주입 (룰이 놓침)    · 룰 밖 하자도 하자로 판정
     · False Positive 주입 (오탐)         · 은행 재량 노이즈 (양방향)
              │                                   │
              ▼                                   ▼
        피처 (X 의 group 1)                   라벨 (y)
```

**두 채널은 서로를 참조하지 않는다.** `review.py` 는 `rule_sim.py` 를 import 하지 않고,
그 반대도 마찬가지다. 이것이 이 설계의 핵심 불변식이다.

### 이 구조가 만드는 것

| 케이스 | 룰 발화 | 은행 판정 | 모델이 배워야 할 것 |
|---|---|---|---|
| 명백한 기한 초과 | 발화 | 하자 | 룰만으로 충분 (모델 기여 없음) |
| 룰이 놓친 `:47A:` 자유서식 미충족 | 미발화 | 하자 | **다른 피처군으로 예측** ← 모델의 가치 |
| 경계값 오차 (±10% 근처) | 발화 | 수리 | **오탐 억제** ← 모델의 가치 |
| 저품질 스캔 + L/C 복잡 | 미발화 | 하자 (재량) | **복합 위험 포착** ← 모델의 가치 |

3·4행이 존재해야만 "결합 > 룰 단독"이 측정 가능하다.

### 두 채널 독립만으로는 부족하다 — 중첩 요건

**v1 설계의 결함.** 초판은 "룰 밖 하자 35%"만 규정하고 그 하자가 남기는 피처 흔적이
어떤 분포여야 하는지를 규정하지 않았다. 그 결과 생성기가 룰 밖 하자마다
**결정론적 워터마크**를 찍었고, 검증에서 네 유형 전부 단일 피처로 완전 분리됨이 측정됐다.

| 하자 유형 | 분리 피처 | 단일 피처 AUC | 중첩 |
|---|---|---|---|
| `freeform_47a_unmet` | `lc_47a_char_length` | **1.000** | 없음 (하자 최소 342자 vs 무하자 최대 268자) |
| `goods_wording_diff` | `dc_max_edit_distance_ratio` | **1.000** | 없음 (0.72 vs 0.05) |

이러면 "결합 > 룰 단독"이 **설계상 보장**된다. 어떤 학습기든 이 피처를 찾아내고,
실제 서류에는 존재하지 않을 신호로 성능을 낸다. 논문에서 방어할 수 없다.

**요건.** 룰 밖 하자의 피처 흔적은 **무하자 건의 자연 변동과 겹쳐야 한다.**
구체적으로:

1. **무하자 건에도 같은 축의 변동을 준다.** `:47A:` 조건문은 무하자 건도 길이가
   변하고, 품명 표기는 무하자 건도 약어·어순·단위 표기 차이로 편집거리가 붙는다.
2. **하자는 그 분포를 이동시킬 뿐, 분리하지 않는다.** 예: 무하자 편집거리
   0.00~0.40, 하자 0.15~0.60 → 겹치는 구간이 존재.
3. **흔적이 아예 없는 유형도 두지 않는다.** `signer_authority_ambiguous` 등은
   현재 흔적이 0인데, 이러면 모델이 배울 것이 없어 라벨 노이즈로만 작용한다.
   약하고 겹치는 흔적을 준다.

### 검증 방법 (Fable 검증 항목)

생성된 데이터셋에 대해 다음을 확인한다.

- `y` 와 `rv_any_critical` 의 상관계수(φ)가 **0.95 미만**일 것. 0.98 이상이면 누수.
- 룰 미발화 건 중 하자 비율이 **0.10 이상**일 것 (룰 밖 하자 존재 증명)
- 룰 발화 건 중 수리 비율이 **0.10 이상**일 것 (오탐 존재 증명)
- **룰 밖 하자 유형별 단일 피처 최대 AUC가 `0.85` 미만일 것** ← 신규.
  0.95 이상이면 완전분리로 간주하고 생성기를 고친다.
- **무하자 건과 하자 건의 피처 분포 범위가 각 축에서 겹칠 것** (min/max 구간 교집합 ≠ ∅)

## 3. 패키지 구조

**모든 작업은 새로 만드는 `ai/defect_model/` 한 디렉토리 안에서 자기완결적으로 수행한다.**
기존 `src/smart_e_bl/` 는 이번 단계에서 건드리지 않는다 (스키마·모델이 이미 안정 상태이고,
룰엔진·API가 아직 없어 결합할 대상이 없다). 앱과의 연결은 8단계에서 별도로 한다.

```

  features.py          # ★ 피처 계약. 학습·추론 단일 진입점
  synth/
    __init__.py
    pools.py           # AI Hub 라벨 → 값 분포 풀 추출 (1회 실행, 캐시)
    generator.py       # 정합성이 완전한 선적 세트 생성
    injector.py        # 하자 주입 (+ 주입 내역 기록)
    rule_sim.py        # [채널 A] 룰 발화 시뮬레이터 (FN/FP 포함)

  train.py             # 분할 → 학습 → 보정 → 평가 → 아티팩트
  calibration.py       # 확률 보정 (별도 분할)
  explain.py           # SHAP 상위 5요인

  cli.py               # python -m ai.defect_model.cli <subcommand>

  data/                # gitignore — 생성물
    pools/             #   AI Hub → 값 분포 풀 (json)
```

**이 디렉토리 밖을 수정하는 것은 두 곳뿐이다** — 루트 `pyproject.toml` 의
optional dependency group 추가(10절)와 `.gitignore` 에
`ai/defect_model/data/` 한 줄 추가. 그 외 기존 파일은 읽기만 한다.

## 4. 피처 계약 (`features.py`)

### 원칙

1. **학습과 추론이 같은 함수를 쓴다.** `extract_features(snapshot) -> dict[str, float]` 하나만 존재.
2. **컬럼 순서는 `FEATURE_SPECS` 로 고정.** `to_vector()` 는 이 순서로만 벡터화.
3. **스키마 버전을 박는다.** `FEATURE_SCHEMA_VERSION = "fs-1"`.
   피처 추가·삭제·의미 변경 시 버전을 올린다. 룰 코드 목록 변경도 버전 변경 사유다.
4. **결측은 0이 아니라 NaN.** XGBoost가 결측을 네이티브 처리한다.
   `tm_days_to_expiry = 0`(오늘 만료)과 `NaN`(L/C 없음)은 완전히 다른 의미다.
   각 `FeatureSpec` 은 `missing_policy` 를 명시한다.
5. 실제 사용한 벡터를 `defect_prediction.feature_snapshot` (jsonb)에 그대로 저장한다.
   학습/추론 스큐 사후 검증의 유일한 근거다.

### 피처 명세

기획안 5.3의 피처군 6개를 그대로 따른다. 총 **82 피처**.

#### Group 1 — RULE_VIOLATION (46)

| 피처 | 타입 | 결측 정책 |
|---|---|---|
| `rv_<RULE_CODE>` × 40 | binary | 0 (미발화) |
| `rv_critical_count` | int | 0 |
| `rv_warning_count` | int | 0 |
| `rv_info_count` | int | 0 |
| `rv_severity_weighted_sum` | float | 0 · Critical=3, Warning=2, Info=1 |
| `rv_distinct_field_count` | int | 0 |
| `rv_any_critical` | binary | 0 |

`RULE_CODES` 는 `features.py` 안에 **동결된 리스트**로 둔다 (기획안 10.1 컷라인: 40개
= UCP600 계열 20 · L/C 조건 10 · 서류 간 정합성 10). 룰 카탈로그가 늘어도
피처 스키마 버전을 올리기 전까지는 벡터 폭이 변하지 않는다. 재현성 요건.

#### Group 2 — DOC_CONSISTENCY (7)

`dc_max_edit_distance_ratio`, `dc_mean_edit_distance_ratio`, `dc_qty_deviation_ratio`,
`dc_weight_deviation_ratio`, `dc_amount_deviation_ratio`, `dc_conflict_field_count`,
`dc_party_name_mismatch_count`

편차율은 `abs(a-b)/max(a,b)`. 비교 대상이 없으면 NaN.

#### Group 3 — EXTRACTION_QUALITY (10)

`eq_mean_confidence`, `eq_min_confidence`, `eq_required_check_count`(<0.70),
`eq_recommend_check_count`(0.70~0.90), `eq_missing_field_count`, `eq_no_evidence_ratio`,
`eq_src_text_pdf`, `eq_src_scan`, `eq_src_json`, `eq_src_manual` (one-hot)

#### Group 4 — LC_COMPLEXITY (9)

`lc_required_doc_count`(:46A:), `lc_47a_char_length`, `lc_47a_condition_count`,
`lc_has_special_clause`, `lc_is_transferable`, `lc_partial_shipment_allowed`,
`lc_transshipment_allowed`, `lc_amount_tolerance_pct`, `lc_absent`

`lc_absent=1` 인 건은 나머지 8개가 전부 NaN. 기획안 5.3 예외
("L/C 없는 거래는 UCP600 계열 룰 비활성화")에 대응한다.

#### Group 5 — TIME_MARGIN (5)

`tm_days_to_expiry`(:31D:), `tm_days_onboard_to_presentation`,
`tm_presentation_period_remaining_ratio`(:48:), `tm_days_issue_to_onboard`,
`tm_is_over_21d` (UCP600 14(c) 경계)

#### Group 6 — HISTORY (5)

`hist_counterparty_defect_rate`, `hist_bank_defect_rate`, `hist_cargo_type_defect_rate`,
`hist_counterparty_shipment_count`, `hist_is_cold_start`

> ⚠️ **이 피처군은 v2에서 라벨 누수를 일으켰다. 아래 규칙이 그 재발 방지책이다.**
>
> v2 구현은 데이터셋 전체에서 엔티티별 라벨 합을 구한 뒤 자기 그룹을 빼는
> leave-base-out 타깃 인코딩을 썼다. 그 결과 엔티티 안에서 남는 유일한 변동이
> **자기 base의 라벨 합**이 되어, 사실상 자기 라벨의 LOO 인코딩이 됐다.
> 평가셋(변형 1개)에서는 제외되는 base가 자기 자신이라 **한 줄짜리 디코더로
> 라벨을 AUC 1.000으로 복원**할 수 있었다. 학습 홀드아웃 AUC 0.894 vs 봉인
> 평가셋 0.687이라는 0.2 격차의 원인이 전부 이것이었고, "결합 < 룰 단독"이라는
> 결론도 이 버그가 만든 것이었다.

**규칙 1 — 이력은 데이터셋 밖에서 온다.**
생성기가 **별도의 과거 기간(history period)** 선적을 엔티티마다 생성하고,
그 선적들을 동일한 채널 B로 라벨링한 뒤, 관측 비율을 계산한다.
**과거 기간 선적은 X의 행으로 절대 들어가지 않는다.** 학습/평가 어느 쪽에도 없다.

**규칙 2 — 어떤 형태의 타깃 인코딩도 금지한다.**
`X`에 있는 행의 `y`가 같은 `X`에 있는 다른 행(또는 자기 자신)의 피처 값 계산에
들어가면 안 된다. leave-one-out, leave-group-out, out-of-fold 전부 금지.
규칙 1을 지키면 이 문제 자체가 생기지 않는다.

**규칙 3 — 잠재 성향을 실제로 부여한다.**
`EntityPools`에 거래처별 `latent_defect_propensity`(예 Beta 분포에서 추출)와
화물 유형별 성향을 준다. v2는 은행 `strictness`만 있고 거래처 성향이 없어서
`hist_counterparty_defect_rate`에 **정당한 신호가 0**이었다 — 누수 운반체로만
존재했다. 성향이 있어야 이 피처군이 의미를 갖는다.

**규칙 4 — 관측 잡음을 남긴다.**
과거 건수가 적으면 관측 비율이 잠재 성향에서 벗어난다(이항 표집).
`hist_counterparty_shipment_count`가 그 신뢰도를 나타내는 피처인 이유다.
과거 건수는 엔티티마다 다르게(예 0~50건) 뽑고, 0건이면 비율 3개가 NaN이며
`hist_is_cold_start=1`이다.

**검증 (Fable 검증 항목).**
- 각 HISTORY 피처를 엔티티로 그룹화했을 때, 그룹 내 값이 **행마다 달라지지 않을 것**
  (엔티티당 상수여야 한다 — 행별로 다르면 행 고유 정보가 새고 있다는 뜻).
- HISTORY 피처만으로 `y`를 예측했을 때 봉인 평가셋 AUC가 **0.70 미만**일 것.
  (잠재 성향의 실제 예측력 수준. 0.9 이상이면 누수.)
- HISTORY 피처를 제거하고 재학습했을 때 **홀드아웃과 봉인 평가셋의 AUC 격차가
  0.03 이내**일 것. 격차가 크면 다른 곳에도 누수가 있다.

### 피처군 스위치

`extract_features(snapshot, groups=...)` 로 피처군을 선택할 수 있어야 한다.
기획안 10.4의 **"모델 단독" 조건 = Group 1 제외** (82 → 36 피처)로 정의한다.
룰 피처를 넣은 채 "모델 단독"이라 부르면 조건 분리가 성립하지 않는다.

## 5. 합성 데이터 생성 (`synth/`)

### 5.1 값 분포 풀 (`pools.py`)

AI Hub 라벨 4,000건의 `bbox[].data` 를 파싱해 다음 풀을 뽑아
`ai/defect_model/data/pools/*.json` 에 캐시.

- 회사명(shipper/consignee/notify 후보), 항구·지명, 선명, 품명, 중량·용적 수치 범위,
  컨테이너 번호 패턴, 금액 표기 패턴

기존 `ai_sample/B_L_model_v2/src/field_parser.py` 의 정규식·영역 규칙을 재사용한다.
완벽할 필요 없다 — 목적은 정확한 필드 추출이 아니라 **현실적인 값 분포 확보**다.

`eval_report_merged.json` 의 `field_accuracy_by_field` (bl_no 0.994, consignee 0.939,
port_of_loading 0.892 …)는 Group 3 피처의 노이즈 강도로 그대로 사용한다.
필드별 실측 오추출률을 쓰면 "OCR이 흔들리는 필드일수록 하자 확률이 오른다"는
관계를 모델이 현실 분포에서 학습한다.

### 5.2 정합 선적 생성 (`generator.py`)

**선적 1건 = B/L + L/C + 상업송장 + 포장명세서.** 내부 정합성이 완전한 상태로 생성.

파라미터로 노출(기획안 10.3 ②): 항로, 컨테이너 수, L/C 조건 복잡도, 거래처, 은행.

- 금액 = 수량 × 단가 (DERIVE 제약 만족)
- B/L 총 포장 수 = 포장명세서 행 합계 (SUM 제약 만족)
- B/L 양륙항 = L/C `:44F:` (EQ 제약 만족)
- 일자 순서: 발행일 ≤ 적재일 ≤ 출항일, 제출일 ≤ `:31D:`

**시드 고정.** 생성기·주입 규칙·난수 시드를 저장소에 포함해 제3자 재생성 가능하게 한다(10.3).

### 5.3 하자 주입 (`injector.py`)

선적 사본에 하자 1~3건 주입. 주입 유형은 **두 부류로 나눈다.**

| 부류 | 비율 | 예 | 룰 커버 |
|---|---|---|---|
| 룰 커버 하자 | 65% | 21일 초과, 항구 불일치, 수량 합 불일치, 원본 통수 부족 | 있음 |
| **룰 밖 하자** | 35% | `:47A:` 자유서식 미충족, 상품 명세 표현 차이, 서명 자격 모호, 관행 문구 누락 | **없음** |

35%는 임의 수치가 아니라 **1절 해법의 필수 조건**이다. 이 부류가 없으면
모델이 룰 위에 더할 정보가 존재하지 않는다.

주입 시 `injected_defects[]` 에 `{type, field, severity, covered_by_rule}` 을 기록한다.
이것이 두 채널의 공통 입력이다.

#### 룰 밖 하자의 흔적 — 중첩 설계 (1절 중첩 요건 구현)

각 유형에 대해 **무하자 건의 기저 변동**과 **하자 시 이동량**을 함께 규정한다.
기저 변동은 `generator.py` 가, 이동은 `injector.py` 가 만든다.

| 유형 | 축 | 무하자 기저 변동 | 하자 시 | 겹침 |
|---|---|---|---|---|
| `freeform_47a_unmet` | `lc_47a_condition_count`, `lc_47a_char_length` | 조건 1~6개, 조건당 40~180자 | 조건 +1~2개(같은 문구 풀에서 추출) | 예 |
| `goods_wording_diff` | `dc_max_edit_distance_ratio` | 약어·어순·단위 표기 차이로 0.00~0.40 | 0.15~0.60 | 예 |
| `signer_authority_ambiguous` | `eq_min_confidence`, `dc_party_name_mismatch_count` | 자연 분포 | 약한 하향 이동(겹치는 범위) | 예 |
| `customary_wording_missing` | `dc_conflict_field_count` | 자연 분포 | 약한 상향 이동(겹치는 범위) | 예 |

**핵심은 "하자 전용 문자열"을 쓰지 않는 것이다.** `:47A:` 추가 조건은 무하자 건이
쓰는 것과 **같은 문구 풀**에서 뽑고, 달라지는 것은 길이가 아니라 *서류로 충족
여부를 확인할 수 없다는 성질*이다. 품명 차이도 무하자 건이 이미 갖는 표기 변동을
키운 것이지 새로운 토큰이 아니다.

> **금지 패턴.** 하자에만 등장하는 고정 문자열, 무하자 분포의 최솟값 아래로
> 클램프하는 상수, 하자 유형과 1:1 대응하는 플래그성 필드. 전부 워터마크다.

### 5.3.1 하자 분류 재정의 (v4 — 실제 룰엔진 도입)

v3까지 `COVERED_SPECS`는 **가상의 40코드 룰 벡터**를 전제로 작성됐다. 실제 룰엔진
(`ruleEngine/`, 21룰)은 **B/L ↔ L/C만 비교하고 송장·포장명세서 룰이 0개**이므로,
기존 "룰 커버" 7종 중 6종이 실제로는 안 잡힌다. 분류를 실제 카탈로그 기준으로 다시 세운다.

### 룰 커버 (65%) — 실제 엔진이 발화시킬 수 있는 것만

| 하자 유형 | 목표 룰 | 변형 방식 |
|---|---|---|
| `expiry_exceeded` | D008 | **`bl_issue_date`**를 `lc_expiry_date` 이후로 (v3는 `onboard_date`를 바꿔 미탐이었음) |
| `latest_shipment_exceeded` | D002 | `onboard_date`를 `lc_latest_shipment_date` 이후로 |
| `pol_mismatch` | D003 | 선적항을 **풀에서 다른 항구로 교체** |
| `pod_mismatch` | D004 | 양륙항을 다른 항구로 교체 (v3는 `" (ALT)"` 접미사 → 토큰 일치로 통과) |
| `bl_consignee_mismatch` | D005B | B/L 수하인 ≠ L/C 수하인 |
| `goods_desc_mismatch` | D006 | B/L 품명에서 L/C 키워드 제거 |
| `presentation_period_exceeded` | D018 | 제시일을 기간 초과로 |
| `weight_over_limit` | D007 | 총중량을 `lc_max_gross_weight_kg` 초과로 |
| `required_field_missing` | D001/D005/D009~D012B | B/L 필수 필드 하나를 비움 |
| `partial_shipment_violation` | D013 | 분할선적 금지인데 정황 발생 |
| `freight_tolerance_breach` | D017 | 운임을 `lc_freight_amount` 허용범위 밖으로 |

> **금지**: 접미사 부착(`" (ALT)"`)처럼 토큰 일치로 통과하는 변형. 실제로 발화하는지
> **각 spec마다 assert로 검증**한다.

### 룰 밖 (35%) — 구조적으로 엔진이 볼 수 없는 것

엔진이 송장·포장명세서를 **입력으로 받지도 않으므로**, 아래는 상수를 조작하지 않아도
구조적으로 룰 밖이다. 그리고 전부 `dc_*` 축에 **연속적이고 자연 중첩하는 흔적**을 남긴다.

| 하자 유형 | 흔적 축 | `p_detect` 근거 |
|---|---|---|
| `qty_sum_mismatch` | `dc_qty_deviation_ratio` | 0.85 — 송장/BL 수량 불일치는 UCP600 14(d) 고적발 범주 |
| `weight_sum_mismatch` | `dc_weight_deviation_ratio` | 0.75 — 계량 방식 차이로 은행이 관대한 편 |
| `invoice_amount_mismatch` | `dc_amount_deviation_ratio` | 0.85 — 금액은 결제 직결이라 엄격 |
| `invoice_consignee_mismatch` | `dc_party_name_mismatch_count` | 0.80 — UCP600 14(d) 서류 간 상충 |
| `insufficient_originals` | (직접 피처 없음) | 0.85 — full set 미제시는 명백 하자 |
| `freeform_47a_unmet` | `lc_47a_*`, `llm_47a_*` | 0.35 (기존 유지) |
| `goods_wording_diff` | `dc_max_edit_distance_ratio` | 0.45 (기존 유지) |
| `signer_authority_ambiguous` | `eq_min_confidence` 등 | 0.30 (기존 유지) |
| `customary_wording_missing` | `dc_conflict_field_count` | 0.25 (기존 유지) |

**이것이 §6.4가 지적한 "룰 밖 하자 AUC 0.415" 문제의 해법이다.** v3의 룰 밖 4종은 흔적이
약하거나 인위적이었으나, 새 5종은 **송장·포장명세서가 룰 입력에 없다는 구조적 사실**에서
나오고 `dc_*` 편차율에 자연스럽게 연속 분포한다. `p_detect` 값은 숫자를 좋게 만들려고 고른 것이
아니라 ICC 하자 유형 분포(수량·금액 불일치는 고적발)에 근거한다.

### 생성기에 추가할 필드

엔진이 요구하나 `SynthShipment`에 없는 것 — **없으면 해당 룰이 영구히 같은 값**이라
XGBoost에 정보가 0이면서 열만 차지한다.

- B/L: `bl_no`, `measurement_cbm`, `freight_amount_usd`
- L/C: **`lc_port_of_loading`**(D003이 이것 없이는 발화 불가), `lc_consignee`,
  `lc_goods_description`, `lc_latest_shipment_date`, `lc_max_gross_weight_kg`,
  `lc_max_measurement_cbm`, `lc_freight_amount`, `lc_incoterms`, `lc_documents_required`

## 5.3.2 `:47A:` 조건 풀 분할 (v4 — LLM 피처의 근거)

### 왜 필요한가

v3 의 `_apply_freeform_47a_unmet` 은 **무하자 건과 똑같은 풀**에서 조건을 추가한다.
그래서 "검증 불가 조건의 *비율*"은 주입해도 변하지 않고 **개수만** 변하는데,
개수는 이미 `lc_47a_condition_count` 가 갖고 있다. 즉 `llm_47a_verifiable_ratio` 는
현재 DGP 에 대해 **무정보이거나 기존 피처의 개명일 뿐이다.**

### 분할

`LC_47A_CONDITION_POOL` 을 두 부류로 나눈다.

| 부류 | 정의 | 예 |
|---|---|---|
| **검증 가능** | 제시된 서류 세트만으로 충족 여부를 확인할 수 있다 | "BILL OF LADING MUST BE MARKED FREIGHT PREPAID AND CLEAN ON BOARD" |
| **검증 불가** | 서류 밖의 행위·시점을 요구해 서류만으로는 확인할 수 없다 | "BENEFICIARY MUST NOTIFY APPLICANT BY EMAIL WITHIN THREE DAYS OF SHIPMENT" |

### 중첩 요건 (1절) — 여기가 워터마크 재발 지점이다

**무하자 건도 두 부류에서 모두 뽑는다.** 무하자 = 전부 검증가능, 하자 = 전부 검증불가로
만들면 즉시 완전분리다.

- 무하자: 검증불가 비율을 **0.0~0.6** 범위에서 추출
- 하자: 혼합비를 **0.3~0.9** 로 이동
- **0.3~0.6 구간에서 겹친다**

하자는 비율을 *이동*시킬 뿐 분리하지 않는다.

### ⚠️ 오프라인 분류기는 오라클이면 안 된다

`llm_47a_verifiable_ratio` 를 계산하려면 조건문을 분류해야 한다. 그런데
**풀 소속으로 판정하면 주입량을 완벽히 측정하는 오라클**이 되어, 중첩을 아무리
넓혀도 이 피처 하나가 완전분리를 만든다.

따라서 분류는 **문장의 언어적 단서**로만 한다.

- 검증가능 신호: 서류 명사(`BILL OF LADING`, `INVOICE`, `CERTIFICATE`, `PACKING LIST`),
  표기·기재 동사(`MARKED`, `STATED`, `SHOW`, `EVIDENCE`)
- 검증불가 신호: 외부 행위 동사(`NOTIFY`, `CONFIRM`, `ARRANGE`, `INFORM`, `ADVISE`),
  서류 밖 당사자·채널(`BY EMAIL`, `BY FAX`, `APPLICANT`), 시점 표현(`WITHIN ... DAYS OF`)

이 분류기는 **틀린다.** 그 오분류가 곧 현실적인 중첩이며, 없으면 워터마크다.
10단계에서 Gemini 가 같은 일을 더 잘하되 여전히 완벽하지는 않게 수행한다.

**검증**: `separability_diagnostics` 에서 `freeform_47a_unmet` 의 단일 피처 최대 AUC 가
**0.85 미만**이고 분포가 겹칠 것. 넘으면 **문턱을 낮추지 말고** 무하자 쪽 혼합비
범위를 넓힌다.

## 5.4 [채널 A] 룰 발화 — v3 시뮬레이터 → v4 실제 엔진 + 관측 노이즈

> **v3의 `rule_sim.py`는 폐기됐다.** 아래는 역사적 기록이며, 현재 구조는 5.4.1을 본다.

`injected_defects[]` → 룰 발화 벡터(Group 1 피처).

**실제 룰엔진의 불완전성을 반드시 재현한다.** 여기서 완벽한 룰엔진을 시뮬레이션하면
학습/추론 스큐가 생긴다 (실제 룰엔진은 놓치고 오탐한다).

- `covered_by_rule=True` 인 하자 → 해당 룰이 확률 **0.85~0.95**로 발화 (나머지는 FN)
- 무하자 건에도 룰별 **0.5~2%** 확률로 스퓨리어스 발화 (FP)
- `covered_by_rule=False` 인 하자 → 발화하지 않음

> **이 모듈은 임시 대역이다.** 실제 룰엔진(계층 A)이 완성되면 동일한 출력 타입을
> 내는 어댑터로 교체한다. `rule_sim.py` 상단에 이 사실을 주석으로 명시할 것.

### 5.5 [채널 B] 모의 심사기 (`review.py`)

`injected_defects[]` → 은행 판정 `y ∈ {0=수리, 1=하자}`.

**`rule_sim.py` 를 import 하지 않는다. 룰엔진도 import 하지 않는다.**

```
P(하자) = 1 - Π(1 - p_detect[defect.type])   # 주입 하자별 은행 적발 확률
        에 재량 노이즈 적용:
          · 무하자 건이 하자 판정될 확률      base_false_defect_rate  (예 0.05)
          · 하자 건이 수리될 확률              lenient_rate            (예 0.08)
          · 은행별 엄격도 계수 strictness ∈ [0.8, 1.2]
```

`p_detect` 는 ICC/ISBP 공표 하자 유형 분포를 근거로 유형별 상수 테이블로 둔다.
예: 기한 초과 0.95, 서류 간 값 충돌 0.90, 표기 관행 0.35, 명세 표현 차이 0.45.

전체 하자율이 기획안 2장의 실제 수치(**65~75%**)에 맞도록 파라미터를 조정한다.
동시에 균형 표본(50:50) 생성 모드도 제공한다 (10.3 "정상/하자 비율" 요건).

#### 두 개의 백엔드

`review.py` 는 교체 가능한 두 구현을 제공하고 `config.REVIEWER_BACKEND` 로 고른다.

| 백엔드 | 근거 | 요구사항 | 용도 |
|---|---|---|---|
| `constant_table` | 위의 `p_detect` 상수 테이블 | 없음 (오프라인) | 기본값·CI·API 키 없는 환경 |
| `claude` | **Claude가 서류를 읽고 심사** | `ANTHROPIC_API_KEY` | 논문용 데이터셋 |

**`claude` 백엔드가 왜 더 나은가.** 상수 테이블은 결국 제가 손으로 정한 숫자이고,
"어떤 하자가 얼마나 잡히는가"라는 판단이 생성기 저자의 편향에 묶인다.
Claude 백엔드는 **`injected_defects[]` 를 보지 않는다** — 서류 세트(B/L·L/C·송장·
포장명세서)만 받아 UCP600/ISBP 관점에서 수리/하자를 판정한다. 1절의 독립 불변식이
"import 안 함"보다 훨씬 강한 형태로 성립한다: 채널 B가 주입 내역 자체를 모른다.

**계약 (반드시 지킬 것)**

- 프롬프트에 `injected_defects`, `covered_by_rule`, 룰 코드, 룰 발화 벡터를
  **절대 넣지 않는다.** 넣는 순간 채널 독립이 깨진다.
- 모델: **`claude-opus-5`** (심사 판단 품질이 곧 라벨 품질). 대량 문서 문구 생성이
  필요하면 그쪽만 `claude-haiku-4-5`.
- **Batch API** 로 호출한다 (오프라인 생성이므로 50% 절감). 3,000+2,000건 규모에서
  Opus 5 기준 약 $60~90.
- 출력은 **structured output**(`output_config.format`)으로 강제:
  `{verdict: "ACCEPTED"|"REJECTED", reasons: [{code, field, rationale}], confidence: number}`.
- **판정 캐시가 재현성 아티팩트다.** API는 비결정적이므로, 선적 내용 해시 →
  판정을 `ai/defect_model/data/reviews/*.jsonl` 에 캐시하고 **저장소에 포함**한다.
  캐시가 있으면 API를 호출하지 않는다. 제3자는 키 없이 동일 데이터셋을 재생성할 수 있다.
- 실패·거부(`stop_reason == "refusal"`)·스키마 위반은 재시도 2회 후
  `constant_table` 로 폴백하고, 폴백 건수를 데이터셋 매니페스트에 기록한다.

**논문에 반드시 명시할 한계.** Claude 백엔드를 쓰면 모델이 학습하는 것은 "은행의
판정"이 아니라 **"Claude의 판정"**이다. 성능 상한이 Claude의 무역서류 이해도가 된다.
이를 숨기지 말고 데이터셋 구성과 함께 기술한다 (10.4 "결과는 반드시 데이터셋
구성과 함께 보고한다").

### 5.6 데이터셋 규모와 분리

| 데이터셋 | 규모 | 시드 | 용도 |
|---|---|---|---|
| 학습 | 원본 1,000 × 변형 3 = **3,000 선적** | 42 | train + calibration + validation |
| 평가(봉인) | 원본 2,000 × 변형 1 = **2,000 선적** | 20260814 | test. 개발 중 열람 금지 |
| 검수 표본 | 평가셋에서 **200건 층화 추출** | 20260814 | 멘토 실무자 검수(10.3 ⑥) |

기획안 10.3의 "개발·평가셋 분리"를 코드 수준에서 강제한다 —
평가셋 생성은 별도 시드·별도 파일이며, `train.py` 는 평가셋을 최종 지표 산출에만
쓰고 튜닝 경로에서는 읽지 않는다(하이퍼파라미터 탐색은 학습셋 내 홀드아웃에서만).

**평가셋을 2,000으로 키운 이유.** 200건에서는 결합 F1의 95% 신뢰구간이
[0.808, 0.899]로 벌어져 `P(F1 < 0.85) = 0.40` — **"0.85를 넘겼다"는 주장이 통계적으로
성립하지 않는다.** 생성 비용은 사실상 0이므로 표본을 키우는 것이 유일하게
합리적인 선택이다. 기획안의 200건은 사람이 검수할 수 있는 규모의 제약이므로,
평가셋에서 층화 추출한 **검수 표본** 200건으로 그 요건을 충족시킨다 — 기획안
10.3 ⑥("전체의 10% 이상 표본 검수")과도 정확히 맞는다(200/2,000 = 10%).

학습용 3,000: 82 피처에 200행이면 XGBoost가 확실히 과적합한다.

**보고 시 필수.** 모든 지표에 **부트스트랩 95% 신뢰구간**을 함께 낸다.
"결합 F1 0.856"이 아니라 "0.856 [0.84, 0.87]"로 보고한다.
성공 판정은 **신뢰구간 하한**으로 한다 — 점추정이 0.85를 넘었지만 하한이
0.85 아래면 "달성"이라고 쓰지 않는다.

## 6. 학습 (`train.py`)

### 6.1 분할 — 3분할 + 그룹

```
전체 3,000 (groups = base_shipment_id)
  ├── train        60%   부스터 학습
  ├── calibration  20%   확률 보정기 적합 (부스터가 본 적 없어야 함)
  └── validation   20%   조기 종료·하이퍼파라미터
평가셋 200 (별도 파일)   최종 보고 수치
```

**`GroupKFold` / `GroupShuffleSplit` 필수.** 원본 1건에서 파생된 정상본·하자본이
서로 다른 분할에 들어가면 누수다 (같은 회사명·항구·품명을 공유한다).
`groups=base_shipment_id` 로 반드시 묶는다.

### 6.2 하이퍼파라미터

소표본이므로 얕게 간다.

```python
max_depth        = 3~4
min_child_weight = 5
subsample        = 0.8
colsample_bytree = 0.8
learning_rate    = 0.05
n_estimators     = early stopping (validation, patience 50)
scale_pos_weight = neg/pos
random_state     = 42
tree_method      = "hist"
```

`scale_pos_weight` 주의: 자연 비율에서는 **하자가 다수 클래스**(65~75%)다.
따라서 이 값은 1보다 **작아진다**. 기계적으로 `pos/neg` 를 쓰면 부호가 뒤집힌다.

### 6.3 확률 보정 (`calibration.py`)

- 표본이 작으므로 **isotonic 금지, sigmoid(Platt) 사용.**
  isotonic은 수백~수천 표본에서 계단형으로 과적합한다.
- `CalibratedClassifierCV(estimator, method="sigmoid", cv="prefit")` 을
  **calibration 분할**에 적합. train 분할 재사용 금지.
- 보정 전 원점수는 `defect_prediction.raw_score` 에 저장하되
  **API 응답·리포트·화면에 절대 노출하지 않는다** (기획안 5.3, 스키마 COMMENT).

### 6.4 평가 — 3조건 × 2비율

기획안 10.4가 요구하는 표를 그대로 산출한다.

| 조건 | 판정 방식 |
|---|---|
| 룰 단독 | `rv_any_critical == 1` → 하자 예측 |
| 모델 단독 | Group 1 제외 36 피처 학습 모델 |
| 결합 | 82 피처 전체 |

× 자연 비율 표본 / 균형 표본 두 조건에서 각각 보고.

지표: **F1**(임계 0.5 및 최적 임계 둘 다), **ROC-AUC**, **Brier score**,
**캘리브레이션 곡선**(10구간 신뢰도 다이어그램 → png).

성공 판정: 결합 F1 ≥ 0.85 **그리고** 결합 F1 > 룰 단독 F1.

#### ⚠️ 측정된 마진의 출처 — 논문 서술이 달라져야 한다

v3 검증에서 드롭-그룹 절제(ablation)로 마진의 출처를 분해한 결과:

| 조건 | 봉인 평가셋 AUC |
|---|---|
| 룰 단독 (`rv_any_critical` 이진) | 0.7313 |
| `rv_distinct_field_count` 단독 | 0.7775 |
| **룰 피처만 (46개, Group 1)** | **0.7916** |
| 결합 (82개) | 0.7918 |
| 모델 단독 (36개, 룰 제외) | 0.7533 |

**룰 피처 위에 비룰 36개를 얹어도 AUC가 +0.0002 움직인다.** 즉 마진 +0.06의
실체는 "룰이 못 보는 위험을 모델이 포착"이 아니라 **"룰 발화 벡터를 이진 판정보다
잘 읽어내는 것"**이다. 룰 침묵 행 844건 중 484건이 WARNING/INFO 발화를 갖고 있고
(하자율 0.494 vs 진짜 침묵 행 0.369), 이진 베이스라인은 이걸 버리는데 모델은 쓴다.

**그리고 룰 밖 하자는 실제로 탐지되지 않는다.** 룰이 침묵하면서 룰 밖 하자만 가진
양성 행은 침묵 음성 행보다 **낮게** 랭크된다 (AUC 0.415 — 우연보다 나쁨).

**원인 — 이중 억제.** 룰 밖 하자에 ① 피처 흔적 중첩(1절 요건, 필수)과
② 낮은 `p_detect`(0.25~0.35, 5.5의 임의 상수)를 동시에 걸었다. ②가 낮으면
그 하자는 라벨을 거의 바꾸지 못해 **학습할 신호 자체가 없다.** ①은 워터마크를
막기 위해 반드시 필요하지만, ②는 제가 근거 없이 고른 숫자다.

**따라서 다음 중 하나를 선택해야 한다.**

- **(A) 정직한 축소 서술** — 주장을 "룰 위반 벡터의 ML 재점수화가 이진 룰 판정보다
  낫다"로 좁힌다. 통계적으로 견고하고(P=1.000) 방어 가능하지만, 기획안 5.3의
  "룰로 잡히지 않는 복합적 위험을 확률로 표현한다"는 서술은 철회해야 한다.
- **(B) 룰 밖 하자를 학습 가능하게 만든다** — `p_detect`를 올려 라벨에 실제로
  영향을 주게 한다. **단, 숫자가 좋아지도록 고르면 그건 우리가 계속 싸워 온
  실패 모드 그 자체다.** ICC/ISBP 근거를 제시할 수 있는 값이어야 한다.
- **(C) Claude 백엔드로 이 질문을 경험적으로 해소한다** — `p_detect`를 제가 추측하는
  대신, Claude가 서류를 읽고 판정하게 한다. 선행 조건: 현재 `signer_authority_ambiguous`
  와 `customary_wording_missing`은 렌더링된 서류에 나타나지 않아 Claude가 볼 수 없다.
  **서류에 실제로 드러나도록 생성기를 고쳐야 한다.** (C)가 가장 정직하지만 API 키가 필요하다.

## 7. 설명 (`explain.py`)

- `shap.TreeExplainer` 를 **보정 전 부스터**에 적용. 보정기는 단조 변환이므로 순위는 보존된다.
- 상위 5개를 `prediction_factor` 에 `rank 1~5`, `feature_name`, `feature_group`, `shap_value` 로 적재.
- **F4 리포트에서 SHAP 값을 확률의 %p 로 서술하지 말 것.** 단위가 다르다(log-odds 마진).
  "기여도 순위"로만 서술한다. 기획안 5.4의 "LLM은 수치를 생성하지 않는다" 규약과
  리포트 수치 대조 검사에 걸린다.
- `feature_group` 은 `FEATURE_SPECS` 에서 자동 조회 — 하드코딩 금지.

## 8. 레지스트리와 롤백 (`registry.py`)

`model_version` 테이블 운용. 스키마에 `is_active` 부분 유니크 인덱스가 걸려 있어
활성 모델은 항상 1개다 (`model_version_active_uk`).

```
register(version, metrics, label_count)   → is_active=false 로 등록
activate(version)                          → 기존 활성 해제 후 활성화 (단일 트랜잭션)
rollback(to_version, reason)               → rolled_back_from 에 직전 버전 기록
```

기획안 5.3: **재학습 후 검증셋 성능이 하락하면 이전 모델로 자동 롤백.**
`train.py` 는 학습 종료 시 현재 활성 모델의 `metric_f1` 과 비교하고,
하락하면 `activate` 를 호출하지 않은 채 경고와 함께 종료한다.

버전 문자열: `{FEATURE_SCHEMA_VERSION}-{YYYYMMDD}-{짧은해시}` (예 `fs-1-20260814-a3f21c`).

## 12. 반드시 지켜야 할 것 (체크리스트)

- [ ] `review.py` 가 `rule_sim.py` 또는 룰엔진을 import 하지 않는다
- [ ] Claude 백엔드 프롬프트에 `injected_defects`·`covered_by_rule`·룰 코드가 없다
- [ ] 룰 밖 하자 비율 ≥ 35%

- [ ] **무하자/하자 피처 분포가 각 축에서 겹친다**
- [ ] 하자에만 등장하는 고정 문자열·클램프 상수가 없다
- [ ] 평가셋 2,000건, 검수 표본 200건이 층화 추출된다
- [ ] 모든 보고 지표에 부트스트랩 95% 신뢰구간이 붙는다
- [ ] 하이퍼파라미터 탐색이 학습셋 내 홀드아웃에서만 이뤄진다 (민감도 표 포함)
- [ ] **HISTORY 피처가 별도 과거 기간에서 계산된다** (X의 행에서 계산 금지)
- [ ] **어떤 형태의 타깃 인코딩도 없다** (LOO·leave-group-out·out-of-fold 전부)
